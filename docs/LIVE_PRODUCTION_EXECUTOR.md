# Bounded labor and work-order execution

Owner: `df-dfhack-bridge-plane-c-pic.4`. Recovery cases also belong to
`df-dfhack-bridge-plane-c-pic.5`.

`dfmcp_adapter::live_production` executes selected steps of one complete original
semantic plan through the existing workforce/1.17 and work-orders/1.10 owners.
It is a Rust embedding boundary. The host supplies the real family sessions,
their private native and semantic association stores, a canonical citizen
evidence owner with independently issued source authority, and the workforce
connection factory. Existing protocol clients and native coordinators remain
responsible for the actual effects.

## The supported plan is explicit

The complete sealed plan is checked before either family can be contacted. The
closed subset has one to sixteen steps and a canonical archive of at most
64 KiB. Archive traversal is bounded to 4,096 nodes and depth 16; the selected
family boundary additionally bounds the complete parent's predicate complexity.
Every step must be either:

- `SetLabor` for one to 32 selected canonical citizens and one exact labor; or
- a finite `CreateWorkOrder` from the existing wooden bed, door, table or chair
  recipe catalog.

Work orders must be leaves of the dependency graph. Their insertion cannot
release a downstream step that needs finished goods. Conditions, compensation,
mandatory checkpoints, unsupported actions and predicates outside the respective
family's protected precondition subset are refused before contact.

For a labor step with dependents, every original postcondition must be an equality
between a selected citizen's `labor.<requested labor>` field and the requested
boolean, or a nonempty conjunction of those equalities. Such a predecessor may
not carry a temporal obligation. The strict native single-labor readback proves
these exact historical postconditions, including preservation of every other
labor column. A broader native assignment result cannot release a successor.

Leaf postconditions, the complete plan terminal predicate and leaf obligations
remain in the original plan. Executing this subset does not discharge them.

`ProductionLayout::from_plan` derives the bounded consumer layout from that
complete validated original. It exposes the optional assignment StepId, the
actual ordered production StepIds and each order's zero-based storage ordinal.
An ordinal chooses a private history or clock slot; it never changes a semantic
StepId or idempotency key. The executor retains the layout and its existing-worker
requirement so native evidence reads do not repeatedly parse the complete archive.
The generic executor still accepts its broader historical sequencing subset;
only a recognized closed layout may enter the complete-parent monitor.

## Produce with existing workers

An original may instead contain one to four independent finite furniture orders
and no assignment action. Each recipe is distinct. The original order StepIds
start at zero; none has a fabricated workforce dependency. The complete parent
retains every selected production objective and one shared
`ExistingLaborRequirement`: each selected citizen's canonical identity, exact
native historical-figure identity, positive requested labor and positive current
workforce eligibility. Missing, negative, duplicated, unrelated or weakened
requirements refuse this closed shape. Every order retains its original
recipe-matched inventory minimum, sealed inventory increase or exact native
counter/status objective, deadline, cadence and stability requirement.

`ExistingLaborProjection` qualifies the selected workers independently of an
assignment review or receipt. The embedding issues the pinned source policy via
`WorkforceFactory::existing_labor_policy`; a capture or layout cannot grant that
authority. Preparation and the post-dispatch-marker commit boundary each obtain
matching current workforce captures around the final canonical identity refresh,
then recheck original private custody and current authority before insertion.
Every order repeats these checks, including later leaves after prior insertions.
The original empty workforce journal remains a read custodian. No work detail is
changed, and no `ConfigureLabor` grant or `SingleLaborResult::Verified` receipt is
created by this path.

The MCP consumer distinguishes its existing single-order `existing_labor`
request from the new `existing_labor_portfolio` request. Both compile one complete
original; the latter uses the established portfolio histories, per-leaf clocks
and whole-cohort observation policy. Their request identities remain separate.
Existing single-order, assignment-pair and assignment-portfolio bytes are not
rewritten by this extension.

## Selection preserves the parent

The private selected-step value retains the whole `PreparedPlan` and its actual
`StepId`. It does not construct a one-step replacement, change the plan digest,
rebase its anchor, renew its deadline or derive a replacement idempotency key.
Each native association retains the complete parent digest, original selected
step, original key, canonical source and exact native plan/journal identity.

Existing public single-step family entry points continue to require one step.
Selected multi-step reviews cannot enter the legacy whole-goal monitors, whose
one-step assumptions would otherwise conflate the selected effect with the
parent's complete goal.

The executor checks the exact original plan, selected step and complete typed
route on every trait call. A caller cannot bypass dependency checks by invoking
`LiveFamilyExecutor` directly or supplying an invented Applied frontier. The
combined owner retains the family sessions privately and verifies predecessor
evidence in those sessions.

## What releases a dependency

A dependency requires the exact original predecessor's
`SingleLaborResult::Verified` receipt and its retained native/semantic custody.
The owner checks this at advancement boundaries. Work-order evidence refresh
also verifies the predecessor after the native dispatch marker has synchronized,
so loss of predecessor custody during a callback prevents the order setter.

This is proof of a historical selected labor effect. It does not assert current
labor at a later observation or supply arbitrary downstream preconditions.
Each family's own independently authorized canonical/native evidence still
guards its current preparation and commit.

The existing native owners require unlimited grants for the named whole
fortress. The combined owner intersects its opening and current grants, carries
the lower risk ceiling and earlier expiry into every nested call, and requires
the native families' Guarded risk level. Entity/map-only or finite-use grants
cannot be widened into that native authority. After a strict queue decode, even
a later source or Query refusal retains the consumed tick. The executor and
durable recovery pin preserve that floor, so an older context cannot revive it.
The native floor belongs to the owner's original restore epoch. Within an
established owner, a later epoch can inspect historical custody under current
Query authority, but cannot use that owner for fresh queue observation or
production control. Old-incarnation ticks do not expire that later epoch's
historical Query authority.

`NativeOrderCreation::Inserted` proves the exact finite order was inserted into
the queue. It does not prove material availability, a workshop, execution,
produced items, physical quiescence or the complete original goal. The combined
owner never reports original-goal completion from all native receipts being
present.

## Seal an observed inventory increase before insertion

`InventoryBaselineProjection::new` accepts one complete Operations/1.3 capture
at the original paused citizen-plan tick, before a Created receipt exists.
It builds a local source projection without replacing the canonical citizen
anchor. The embedding independently verifies its world, software and operations
generation, issues complete Item coverage and exact type/stack-size source
grants, and calls `increase` to derive the count. An incomplete census refuses;
it cannot become a zero baseline.

The resulting `ObservedInventoryIncreaseObjective` retains the original count,
a positive requested increase, checked absolute target, original anchor,
complete operations digest, native generation and the next-job, next-building
and next-item counters. These are typed predicate fields covered by the existing
immutable plan archive and independently expected archive identities. No raw
baseline census is separately archived, and offline recovery makes no claim
that it recounted that census.

`ObservedInventoryGoal` recognizes either the unchanged minimum or the exact
new increase shape. Growth cannot be substituted for a legacy objective.
Current goal polling and durable-history replay both reject a native generation,
tick or allocator frontier older than the sealed baseline, including before the
first goal sample. They independently qualify each current complete inventory.

An increase measures net matching stack units relative to that original
census. Replacing item IDs without growing stock does not satisfy it; increases
in existing stacks can. Consumed or removed goods reduce the current total.
Neither type proves that the original order produced the items, that they have
the requested material, or that they are usable. Original keys, deadlines,
cadence and stability remain unchanged through retirement and recovery.

## Selected original production goals

After the exact original work-order insertion is verified, the executor can
open a separate `SelectedWorkOrderGoalMonitor` and poll it through
`poll_selected_order_goal`. This exclusive wrapper keeps the complete original
parent and archive seal, actual selected StepId, original key, native review,
insertion receipt and historical labor dependencies together. The mutable family
sessions and inner monitor remain private. Legacy public one-step monitor and
history APIs still refuse a selected multi-step review before source contact.

Each sample evaluates the selected step's original postconditions and temporal
obligation together. The complete parent's terminal predicate is evaluated
separately. A true inventory objective cannot substitute historical labor
readback for current labor evidence or establish the whole parent's goal. An
explicit recipe-matched `observed_inventory_minimum` can remain true after the
finite native order retires; existing and unrelated matching items count. This
proves neither material, eligibility nor causal production by that order.
An explicit `observed_inventory_increase` uses the same complete current census
but requires the sealed baseline plus the requested increase; preexisting stock
alone cannot satisfy it.

The existing bounded durable history stores raw source captures and publication
boundaries under the exact selected identity. Replay reissues independently
accepted source policy, preserves first achievement and terminal history, and
withdraws current proof and unfinished stability. Original deadlines, cadence
and stability are never renewed. Failed outer publication can invalidate the
current sample without additional I/O; the next admitted poll persists the
interruption. Predecessor custody is checked around replay and every live policy
callback, with a final complete-family verification before success is returned.
A missing, uncertain or replaced original insertion cannot start this monitor.

For the closed original two-step labor/order pair,
`Executor::poll_selected_parent_goal` additionally brackets the selected inventory
sample with exact current workforce captures. Independent labor and inventory
policies qualify the joined evidence. `SelectedParentGoalProgress` evaluates the
unchanged complete parent terminal at a new composite anchor, preserving the
selected inventory anchor separately. Complete-parent proof requires both current
parent truth and the original selected temporal proof. It does not introduce a
new obligation, renew a deadline, or infer current labor from a native receipt.
Its bounded `labor` findings compare the exact original selected citizen/labor
settings under the independent workforce policy before any child policies are
combined. Canonical-ID order is deterministic. Unqualified values remain unknown
and never appear as observed Booleans; the combined anchor and workforce source
digest bind the diagnostics to the same sample as parent truth.

This parent result is process-local. It is never recovered from inventory-only
history. Any failed acquisition or publication withdraws current proof and
unfinished selected stability; consumed native source floors remain retained.
Within-bracket drift, changed original citizen identity, source regression,
policy withdrawal and custody loss refuse publication. The combined development
MCP host consumes this path through its existing foreground Wait operation.

## Bounded portfolio source and proof ownership

The combined consumer also compiles one original labor action and one to four
finite furniture leaves, or one shared existing-worker prerequisite and one to
four independent furniture leaves. `open_private_portfolio_order_goal_monitor`
and `begin_portfolio_order_goal_monitor` explicitly
opens a separate strict source-cursor lane for each selected review. Its strong
owner is retained by exact review seal, bounded to four; reopening that same
review invalidates its prior owner. Each lane retains its own canonical floor.
The semantic order owner still shares native incarnation, native sequence and
authority tick floors across all leaves. Legacy original and selected-pair
monitor APIs keep their existing single-owner and canonical-gap rules.

`poll_selected_portfolio_goal` publishes one selected labor/production pair at a
separate parent publication cursor. It cannot call that pair the complete
original goal. `compose_production_portfolio_goal` accepts only adapter-owned
qualified results and joins all original leaves inside one complete progress
bracket. It rechecks every exact source policy, common raw operations and labor
capture, selected receipt/native identity, paused tick and complete original
terminal predicate. The new composite digest binds all original samples and
outer captures. A subset, caller truth flag or historical receipt cannot
substitute for any member.

`compose_existing_labor_portfolio_goal` applies that complete-cohort contract to
the dependency-free layout and reissues each existing-worker source policy.
Every leaf retains the same complete prerequisite and exact workforce capture.
Its selected parent sample proves only that leaf together with current workers;
even a one-order portfolio waits for the explicit whole-cohort composition.
Different stock captures, changed worker identities, withheld policy or an
incomplete set of original leaves refuse the join. Later labor loss can make
the current whole parent False while each order's historical achievement remains
immutable. Inventory objectives can still be sampled after normal order
retirement without attributing those items to the original orders.

Clock custody accepts a dependency-free order only through the recognized
existing-worker layout. Its identity still binds the complete parent archive,
the actual selected StepId and key, exact native Created receipt and original
deadline. StepId zero is a real order here. Storage-slot numbering is separate,
and neither clock authority nor a preparation is reconstructed from this mapping.

The host samples one leaf per shrinking-budget Wait. A successful owned clock
withdraws current certificates without fabricating a source gap in an inactive
leaf; each later qualified sample remains strictly consecutive within its own
history. Failures and restart preserve the existing unfinished-stability reset.
A whole-parent publication cursor advances from the retained public and selected
source number floors but always carries a newly composed hash. A failed outer
publication cannot strand recovery behind an already consumed source sequence
or promote a selected-only hash to the public parent anchor.

## Recovery and integration boundary

Use this executor with the durable coordinator described in
[`LIVE_MUTATION_DISPATCH.md`](LIVE_MUTATION_DISPATCH.md). That coordinator retains
the complete original archive and execution frontier before family contact.
After a lost reply or restart, recovery consults the original native keys under
Query authority. It neither constructs a replacement operation nor restores a
process-local review or native dispatch permit.

Canonical evidence refresh reacquires the original paused citizen observation;
it cannot allocate a replacement cursor or silently rebase the plan. Canonical
citizen and native family generations remain separately bound. Their numeric
generation counters need not match.

The adapter boundary itself adds no MCP tool, bridge method, protocol generation,
source issuer, capability grant, production runner or admitted live tuple.
The separate [combined development MCP host](COMBINED_PRODUCTION_MCP.md) consumes
this executor and durable coordinator through the existing eleven tools. It
retains one original labor/order plan or bounded furniture portfolio with parent archive/identity
custody and independently pinned real family shells. Concrete native clients
remain unadmitted development implementations.
Synthetic component execution is distinct from full workspace, ambient runtime,
native DFHack and live-fortress qualification.
